# KR580VM1 (КР580ВМ1)

The KR580VM1 is a Soviet microprocessor that extends the KR580VM80A (an Intel
8080 clone). It is binary compatible with the 8080: every 8080 program runs
unchanged. On top of that it adds an alternate register pair, a second 64K
data bank, ten instructions and two prefix bytes.

Almost nothing about this chip is written up in English, so this page records
what the original Russian instruction-set document says, together with the
places that document contradicts itself.

|---|---|---|
| `z88dk-dis` | `-mvm1` | complete |
| `z88dk-ticks` | `-mvm1` | complete |
| `z88dk-z80asm` | `-mvm1` | complete |
| `sccz80` / `80cc` | `-mvm1` | complete |
| `zcc` | `-mvm1`, `+test -clib=vm1`, `+z80 -clib=vm1` | complete |
| classic C library | `vm1_crt0.lib`, `testvm1_clib.lib`, `vm1_clib.lib` | complete |
| float | `--math-mbf32` (`mbf32_vm1.lib`) | complete |

`math32` and `math16` have no vm1 build. Their 8085 cores are written around
`LDSI` (`ld de,sp+n`) and `RDEL` (`rl de`), and the KR580VM1 uses both of those
opcodes for something else (see [Comparison with the 8085](#comparison-with-the-8085)),
so those libraries need an 8080-style port before a `_vm1` product can exist.
`--math-mbf32` is the working float option.

### `pop af` is not free here

`POP PSW` loads MF from bit 3 of the popped byte, and MF selects the data bank
for *every* data access — pushes, pops and `ret` included. So the two idioms
that treat AF as a spare 16-bit register are both unsafe:

* `pop af` as a stack discard, and
* `push bc` / `pop af` as a register move.

Either one switches the bank whenever bit 3 of the popped byte happens to be
set, which makes it data-dependent and easy to miss in testing. A matched
`push af` … `pop af` pair is fine: MF round-trips.

`sccz80` and `80cc` already avoid emitting the idiom
(`CPU_POP_AF_IS_SAFE()`); it is hand-written assembler that needs the guard.

**The same trap, one CPU wider.** A `pop af` … `push af` pair that carries a
*return address* is broken on the 8080 and 8085 as well, for a different
reason: their flags byte cannot hold arbitrary data. Bit 1 always reads 1 and
bits 3 and 5 always read 0, so `push af` hands back a different low byte and
the routine returns to the wrong address. On the Game Boy CPU the whole low
nibble reads 0. 64 library wrappers now carry an
`IF __CPU_INTEL__ | __CPU_GBZ80__` arm that keeps the return address in a
register pair. This was a live bug: `HeapInfo_callee` returned to `$03D3`
instead of `$03D9` on the 8080, which walked the stack pointer up through the
whole address space until it overwrote the code.

There is no `lib/arch/vm1/vm1_rules.1`. zcc treats a missing CPU rules file as
"no CPU-specific peepholes" and the build is correct without one; a vm1 rules
file would only add DSUB / LHLX / SHLX / ANX / ORX / XRX peepholes.

### Known errata in the primary document

Both were resolved against the emuverse copy and against 8085 precedent.

1. **SHLX is listed as `11001101`**, which is `$CD` — the 8080's `CALL`. The
   real encoding is `$D9`, matching the 8085. LHLX at `$ED` is listed
   correctly.
2. **The SMF0/SMF1 tables show a `00111000` (`$38`, RS) prefix byte**, but
   the surrounding prose and the section headings both say MB. The encodings
   are `$28 $00` and `$28 $7F`.

## Registers

Identical to the 8080, plus one addition:

```
  A   F                    F = S Z OF AC MF P 1 CY
  B   C                        7 6  5  4  3 2 1  0
  D   E
  H   L      <- the pointer pair
  H1  L1     <- the alternate pointer pair, reached through the RS prefix
  SP
  PC
```

The document calls HL and H1L1 collectively the *pointer pair*
(регистровая пара-указатель). z88dk spells H1/L1 as `h'`, `l'` and `hl'`.

H1L1 is not a shadow bank in the Z80 sense — there is no exchange
instruction. Each instruction independently chooses which pair it uses, via
the RS prefix.

## Flags

The 8080's flag byte gains two flags in bits that the 8080 left as a constant
0 and a copy of A:

| Bit | Name | Meaning |
|---|---|---|
| 7 | S | sign — bit 7 of the result |
| 6 | Z | result is zero |
| 5 | **OF** | signed overflow: carry into bit 7 without carry out, or vice versa |
| 4 | AC | half carry out of bit 3 |
| 3 | **MF** | current data bank: 0 = main, 1 = additional |
| 2 | P | parity — set when the number of 1 bits is even |
| 1 | — | unused, permanently 1 |
| 0 | CY | carry |

Note that bit 2 is **parity in all cases**, as on the 8080 — signed overflow
lives in its own bit rather than sharing the parity bit as it does on the Z80.

## Memory

The address space is two 64K banks, called the *main* and *additional* banks.

- **Instructions are fetched only from the main bank.** The additional bank
  holds data only.
- Data accesses use the bank named by the MF flag.
- The MB prefix flips the bank for the following instruction only.
- `SMF0` and `SMF1` set MF permanently.

The document's wording covers data access generally and carves out no
exception for stack operations, so `PUSH`/`POP`/`CALL`/`RET` follow MF too.
This is the reading z88dk implements, but it is an inference rather than an
explicit statement, and it means changing MF between a `CALL` and its `RET`
will not work.

## The prefixes

A prefix field of up to two bytes may precede any opcode. The opcode field is
one byte and may hold any value **except** `$28` and `$38`.

### RS — `$38`, 4T

Substitutes H1/L1 for H/L in the following instruction: as source, as
destination, and as the `(HL)` memory pointer. `XCHG` is the one H/L
instruction the document gives no RS form for — it always exchanges DE with
the real HL.

```
    38 7E     ld   a,(hl')        A <- M(H1L1)
    38 7C     ld   a,h'
    38 21 nn  ld   hl',nnnn
    38 E5     push hl'
    38 09     add  hl',bc
```

### MB / CS — `$28`, 4T

One byte with two jobs, depending on what follows it.

**In front of a memory instruction it is MB**, and flips the data bank for
that instruction:

```
    28 7E     mb ld a,(hl)        A <- M1(HL), i.e. the other bank
```

**In front of `DAD`, `DSUB` or `DCMP` it is CS**, and makes them consume the
carry flag. z88dk folds this into the mnemonic rather than printing a
separate prefix word:

```
    09        add hl,bc           HL <- HL + BC
    28 09     adc hl,bc           HL <- HL + BC + CY
    08        sub hl,bc           HL <- HL - BC
    28 08     sbc hl,bc           HL <- HL - BC - CY
    CB        cp  hl,bc           flags from HL - BC
    28 CB     cpc hl,bc           flags from HL - BC - CY
```

`cpc` is a z88dk coinage; the document gives no Zilog-style name for
compare-with-borrow.

Both prefixes may be combined, MB first:

```
    28 38 08  sbc hl',bc
```

A run of prefixes does not cancel: each one affects the instruction that
eventually follows.

## The added instructions

Timings are for the bare instruction; each prefix byte adds 4T.

| Opcode | z88dk mnemonic | Doc name | Operation | T |
|---|---|---|---|---|
| `08` | `sub hl,bc` | DSUB B | HL ← HL − BC | 10 |
| `18` | `sub hl,de` | DSUB D | HL ← HL − DE | 10 |
| `10` | `ld (hl),and (hl)` | ANX | (HL) ← (HL) & A | 10 |
| `20` | `ld (hl),or (hl)` | ORX | (HL) ← (HL) \| A | 10 |
| `30` | `ld (hl),xor (hl)` | XRX | (HL) ← (HL) ^ A | 10 |
| `CB` | `cp hl,bc` | DCMP B | flags from HL − BC | 10 |
| `DD` | `cp hl,de` | DCMP D | flags from HL − DE | 10 |
| `D9` | `ld (de),hl` | SHLX | (DE) ← L, (DE+1) ← H | 10 |
| `ED` | `ld hl,(de)` | LHLX | L ← (DE), H ← (DE+1) | 10 |
| `FD nn nn` | `jp of,$nnnn` | JOF | jump if OF is set | 10 |
| `28 00` | `smf0` | SMF0 | MF ← 0 | 8 |
| `28 7F` | `smf1` | SMF1 | MF ← 1 | 9 |
| `28` | — | MB / CS | prefix | 4 |
| `38` | — | RS | prefix | 4 |

All ten sit in encodings the 8080 wastes: the `$x8`/`$x0` column of the first
quarter of the map, and the four undocumented `$CB`/`$D9`/`$DD`/`$ED`/`$FD`
prefix slots.

### Timing model

Every timing in the document decomposes as **4T per prefix byte plus the bare
instruction**, with no exceptions — `RS MOV <D1>,<S1>` is 9T = 4 + 5,
`MB RS MOV <D1>,M1` is 15T = 4 + 4 + 7. Base instruction timings are identical
to the 8080 throughout.

The document lists only the taken case for conditional branches. The
not-taken costs are not stated; z88dk follows the 8080:

| | taken | not taken |
|---|---|---|
| conditional jump | 10T | 10T |
| conditional call | 17T | 11T |
| conditional return | 11T | 5T |

### Flags set

| Instruction | S | Z | OF | AC | P | CY |
|---|---|---|---|---|---|---|
| DSUB | ● | ● | | | | ● |
| DCMP | ● | ● | | | | ● |
| DAD | | | | | | ● |
| ANX / ORX / XRX | ● | ● | | | ● | 0 |

DSUB sets S from bit 15 of the result. The logical memory ops clear CY and
leave OF and AC alone.

## Comparison with the 8085

The two chips extend the 8080 in the same undocumented opcode slots but do
not agree on what goes there. Only DSUB, SHLX and LHLX line up.

| Opcode | 8085 | KR580VM1 |
|---|---|---|
| `08` | `sub hl,bc` (DSUB) | `sub hl,bc` (DSUB) — same |
| `10` | `sra hl` (ARHL) | ANX |
| `18` | `rl de` (RDEL) | DSUB D |
| `20` | `rim` | ORX |
| `28` | `ld de,hl+n` (LDHI) | MB/CS prefix |
| `30` | `sim` | XRX |
| `38` | `ld de,sp+n` (LDSI) | RS prefix |
| `CB` | `rst v` (RSTV) | DCMP B |
| `D9` | `ld (de),hl` (SHLX) | SHLX — same |
| `DD` | `jp nk` (JNK) | DCMP D |
| `ED` | `ld hl,(de)` (LHLX) | LHLX — same |
| `FD` | `jp k` (JK) | JOF |

The 8085's extra flag is K (bit 5), a signed-comparison result; the VM1's is
OF, plain signed overflow. They occupy the same bit but are not the same
thing.

## Using the z88dk tools

```sh
# disassemble
z88dk-dis -mvm1 -o 0x100 program.bin

# emulate
z88dk-ticks -mvm1 program.bin -end 0x2000
```

### Emulator notes

- The alternate pair is implemented by exchanging `h`/`l` with the otherwise
  unused Z80 shadow registers `h_`/`l_` for the duration of one instruction.
  `EX AF,AF'` and `EXX` do not exist on this CPU, so that register file is
  free.
- Interrupts are held off between a prefix and its instruction, as they are
  for the Rabbit's `altd`/`alts`.
- OF is derived from the same operand history the Z80 overflow flag uses, and
  is stored in the slot the 8085 uses for K.
- The `$ED $FE` escape that z88dk uses for emulator hooks is preserved, so
  `ld hl,(de)` with `$FE` in the next byte is a hook rather than an LHLX.
- Base instruction timings follow the 8080.
